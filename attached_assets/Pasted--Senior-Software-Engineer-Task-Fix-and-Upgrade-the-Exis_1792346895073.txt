# Senior Software Engineer Task: Fix and Upgrade the Existing Authentication System

Act as a senior full-stack software engineer, authentication specialist, backend security engineer, and UI/UX designer.

Thoroughly inspect the existing application, identify the root causes of authentication bugs, and implement, improve, and test the authentication system. Focus exclusively on login, registration, OTP verification, business account authentication, and related authentication security.

## Critical Instructions

- Do not rebuild the entire application.
- Do not replace working systems unnecessarily.
- Preserve all existing features, business logic, database records, API integrations, AI functionality, demo payment systems, and page designs outside the authentication module.
- **OTP MUST operate in DEMO MODE ONLY.**
- Generate a new random six-digit OTP code for each verification request.
- Never use a permanently fixed OTP code such as `123456`.
- Display the generated demo code directly on the OTP verification screen.
- Do not send real SMS messages or require a paid SMS provider.
- Keep all authentication changes compatible with the existing project architecture.

## 1. Dynamic Demo OTP Phone Authentication

Implement a fully functional Dynamic Demo OTP verification system.

### Phone Number Input

- Support Uzbek phone numbers using the format `+998 (90) 123-45-67`.
- Validate phone numbers before allowing users to continue.
- Normalize phone numbers consistently before account lookup or storage.
- Prevent incomplete, invalid, or incorrectly formatted phone numbers from proceeding.
- Provide clear, user-friendly validation messages.

### Dynamic OTP Generation

1. Generate a new random six-digit numeric OTP code whenever a user requests verification.
2. Generate another new code whenever the user requests a resend.
3. Use a cryptographically secure random number generator on the backend whenever supported by the existing architecture.
4. Never use a permanently hardcoded OTP code.
5. Ensure every newly generated code differs from the immediately previous code for that verification session. If the generated code matches the previous code, generate another one.
6. Generate and validate codes through the existing backend or authentication infrastructure whenever possible.
7. Do not rely solely on frontend JavaScript to authenticate users.
8. Bind every code to the correct normalized phone number and verification session.
9. Prevent codes issued for one phone number or session from verifying another.
10. Store and manage verification state securely using the existing infrastructure. Avoid storing plaintext OTP codes in persistent storage when secure alternatives are available.

### Displaying the Demo OTP

Because this application uses Demo OTP mode, display the generated code clearly on the verification screen.

Example:

`DEMO MODE | Your verification code: 482731`

Requirements:

- The displayed code must exactly match the code validated by the backend.
- Update the displayed code whenever a new OTP is generated.
- Clearly identify the flow as a demonstration.
- Do not claim that an SMS has been sent or delivered.
- Do not require a real SMS provider, SMS API key, or paid messaging service.
- Keep the OTP interface clean, responsive, and consistent with the application's existing design.

### OTP Input Interface

Implement six separate OTP input boxes with:

- Automatic focus movement between boxes.
- Support for pasting the entire six-digit code.
- Correct backspace and keyboard navigation.
- Numeric input and mobile-friendly keyboards.
- Clear focus indicators and accessible labels.
- Automatic submission only when appropriate and without creating duplicate requests.
- Clear visual feedback for loading, success, incorrect codes, expired codes, and errors.

### OTP Expiration and Countdown

- Set the default OTP validity period to 60 seconds.
- Display an accurate countdown timer on the verification screen.
- Reject expired codes on the backend, regardless of frontend timer state.
- Disable or restrict verification after expiration.
- Show a clear message when a code expires.
- Allow the user to request a new code when permitted.

### Resend OTP Behavior

Implement a functional resend-code process.

- Start a 60-second resend countdown after a successful code-generation request.
- Prevent resend requests while the countdown is active.
- When a resend is permitted, generate a new six-digit code.
- Ensure the new code differs from the immediately previous code for the same verification session.
- Immediately invalidate the previous code when the new code is issued.
- Reset the validity timer and update the displayed demo code.
- Prevent duplicate resend requests and excessive requests.
- Handle failed requests gracefully without displaying a code that the backend did not successfully issue.

### OTP Verification Rules

- Accept only valid six-digit codes associated with the correct phone number and verification session.
- Reject incorrect codes.
- Reject expired codes.
- Reject previously used codes.
- Invalidate the code immediately after successful verification.
- Prevent OTP replay, reuse, expiration bypasses, and duplicate verification requests.
- Enforce reasonable verification-attempt and resend limits on the backend.
- Handle concurrent requests safely so that only the current valid code can be accepted.
- Display understandable error messages without exposing sensitive internal information.

### Demo Mode Security Limitations

This is a demonstration system, not production-grade identity verification.

- Clearly label all demo verification screens.
- Never represent a displayed demo code as proof of real-world identity.
- Do not silently switch between demo and production authentication.
- Do not allow demo OTP behavior to bypass production authentication controls.
- Keep the demo verification logic separate from any existing production authentication configuration.
